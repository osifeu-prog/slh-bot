### Case Study: SLH — מטוקנים לשיטת עבודה

הקורס התחיל מעלות AI, אבל היישום החשוב יותר הוא ארכיטקטורה.

ב-SLH אנחנו רוצים שכל שינוי משמעותי יעבור דרך שרשרת ניתנת לבדיקה:

FOUND IN CODE
→ IMPORTED
→ REGISTERED
→ RUNNING
→ EXTERNALLY EXPOSED
→ ENABLED BY GATE

זוהי "שיטת עבודה בהשראת בלוקצ׳יין".

### 1. Identity
מי המשתמש? מי הסוכן? מי ביצע את האירוע?

### 2. State
מה היה המצב לפני הפעולה?

### 3. Rule
מה מותר לבצע לפי ההרשאות וה-gate?

### 4. Transition
מה בדיוק השתנה?

### 5. Evidence
איזה commit, event, transaction, log או test מוכיח שהשינוי התרחש?

### 6. Idempotency
אם אותה בקשה מגיעה פעמיים — האם נקבל שינוי כפול או אותה תוצאה?

### 7. Audit
האם אדם אחר יכול להבין בדיעבד מה קרה בלי לסמוך רק על זיכרון של מי שעבד על המערכת?

### 8. Continuation
מהו ה-state האחרון, ומה הפעולה הבאה החוקית ממנו?

### דוגמה מהעולם האמיתי
נניח שמשתמש משלם עבור מוצר דיגיטלי.

מערכת חלשה:
Payment → grant → "מקווים שהכול עבר"

מערכת חזקה יותר:
Payment identified
→ payment verified
→ idempotency checked
→ entitlement granted
→ canonical state updated
→ evidence recorded
→ user can reopen/use entitlement later

אותה חשיבה מתאימה גם ל:
- AI agents
- CI/CD
- מסמכים וחתימות
- שרשרת אספקה
- תעודות לימוד
- מחקר ונתונים
- תשלומים ויישובים
- מערכות שיתופיות

### נקודה חשובה
לא כל מערכת צריכה בלוקצ׳יין אמיתי.
לפעמים DB אטומי, audit log, signatures והרשאות ברורות נותנים את רוב הערך בפשטות ובעלות נמוכה יותר.

המטרה היא לא "להשתמש בבלוקצ׳יין".
המטרה היא לבנות עבודה שאפשר לסמוך עליה, לבדוק אותה ולהמשיך ממנה.
